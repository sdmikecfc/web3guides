# One starter build: onboarding version 2

**Staged only. Do not apply this SQL to a live or shared database without the user's explicit approval after an object-by-object impact review. Doma Reporter, its configuration and its database operations are outside this task. Trading, LP and arbitrage bots remain offline and untouched.**

Apply `bots-onboarding-v1.sql` followed by `bots-onboarding-v2.sql` before enabling the matching preview flags `BOTS_ONBOARDING_V2=1` (server) and `NEXT_PUBLIC_BOTS_ONBOARDING_V2=1` (browser). The second migration is additive and transaction wrapped. It widens the existing version constraint, permits no welcome bot, adds draft/revision fields, and makes coin balances version aware. Existing v1 accounts, older kits, inventory, ledger and browser saves are retained. It can be applied again safely.

Exact staged objects: alter `public.battle_bots_onboarding` (version constraint, nullable `welcome_bot_id`, new `draft_offers`, `draft_name`, `draft_look`, `draft_paints`, `revision`, `finished_revision`, `handoff_fingerprint`, `finished_fingerprint` columns); replace `public.bb_coin_balance(text)`; create `public.bb_onboarding_v2_provision`, `public.bb_onboarding_v2_edit`, `public.bb_onboarding_v2_finish`, and `public.bb_onboarding_v2_handoff`, with execution restricted to `service_role`. `bb_coin_balance` is shared and needs separate dependency review. The new RPCs, if enabled, write game player/bot/progress/part/claim rows and call the existing, unchanged `bb_grant` to write ledger amounts. The prerequisite v1 migration also contains shared money functions: do not apply it automatically to a shared database. No live migration, enrollment, grants or reporter operations were performed during verification.

The flags affect new enrollment only. Rollback must turn both off together: already enrolled v2 players still load and finish through their stored version. An absent v2 migration returns a readable 503 for new enrollment, never an older starter economy. Existing garages remain readable and sign-in does not grant another starter.

## Contract

- Provision inserts exactly one empty bay-1 bot and one protected 250-coin allowance. No premade companion is granted. Player locking and existing inventory/ledger/onboarding checks prevent repeat or mixed-version grants.
- `POST /api/bots/onboarding`: `welcome`; `choose` with `socket`, canonical `offerId`, `revision`; `name` with a fixed-catalogue `name` and `revision`; `finish` with `revision`. A stale revision returns 409 with a refresh instruction. A full set of choices remains editable until Finish.
- `OnboardingView.version` is 1 or 2. V2 exposes `revision`, `draftOffers`, `draftName`; common `purchases` and `purchasedCount` mean selected choices before Finish, with negative virtual IDs. V2 `step` goes from welcome to shop to complete; practice is optional. `draftPreview(view)` creates the virtual preview build and parts. Virtual IDs are never owned inventory or valid inputs to `bot/save`.
- Finish takes the player/progress/bot locks, validates all seven catalogue choices, releases the reserve, debits 250 once, creates seven independent part instances and claims, attaches them to the same bot, and completes onboarding in one transaction. Failed inserts roll everything back. Retrying the same finished revision succeeds without a second debit or grant. Neutral stats are `[1,1,1]`; purchased parts recycle at the existing 40% rule. No battle rewards or results are imported.
- `POST /api/bots/practice-handoff` still receives `{appearance}`. `practiceDraftOf(state,build)` supplies a v2 partial or complete appearance-only payload. The parser accepts only canonical choices, permitted paint and fixed names; cosmetics are normalized from those choices with no earned wins/hats. The v2 handoff RPC saves the whole draft and optionally finishes atomically. Identical retries succeed. A different or already edited wallet draft returns `{applied:false,reason:'existing-garage'}` without changing it. The caller keeps the browser save and offers the wallet or browser garage. Older appearance-only payloads continue working with their original handoff path.
- Local saves keep the existing storage key. `freshGameDemo(2)` and `readGameDemo(raw,2)` opt new visitors in; an existing version-1 save is reconstructed as version 1. `demoBuy` edits v2 previews without spending, `demoSave` updates draft names, and `demoFinish` is the only initial purchase. Completed parts remain permanent and recycling tombstones survive hydration.

## Verification

`scripts/bots-onboarding-v2-check.ts` exercises the actual SQL migration/RPCs in isolated PGlite: repeat enrollment, reserves, wrong slot, stale revisions, replacing an earlier choice, exact identity on Finish, repeated Finish, late injected insert failure and rollback, canonical assembly, partial/complete handoff, handoff conflict, failed partial-complete transfer, repeated migration, and denied public-role RPC execution. It also checks local reloads, editable seven-part previews, explicit Finish, canonical stats and older browser saves. Mixed v1/v2/legacy enrollment in each winning order keeps exactly the original grant/inventory; late complete-transfer failure rolls back its fingerprint and all draft changes so an identical retry can succeed. PGlite queues queries within one process: the row-lock ordering is verified in SQL, but this is not a physical multi-connection load test.

Run with the project's TypeScript test runner and `BOTS_PGLITE_PATH` pointing to an installed PGlite package. Existing regression scripts remain `bots-onboarding-check.ts`, `bots-game-state-check.ts`, `bots-rollout-check.ts`, and `bots-wallet-fight-check.ts`. No production migration or deployment is performed by these checks.
